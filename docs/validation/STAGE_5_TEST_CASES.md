# Stage 5 Comparison Acceptance Cases

These cases define the acceptance oracle for the v1 comparison service. Values
marked **controlled** are test inputs, not provider observations or predicted
lunar conditions. The expected score values below are calculated directly from
the agreed v1 formula; the expected order is written explicitly and is not
generated by a test-side ranking implementation.

The API contract is the source of truth: `docs/API_V1.md` section 11 and
`contracts/openapi.v1.yaml` schemas `ComparisonRequest` and
`ComparisonResult`. Comparison is currently marked planned in OpenAPI and the
runtime route is not registered. These cases are therefore a test plan and
oracle, not evidence of an implemented comparison workflow.

## Shared request conditions

Every request has one top-level set of comparison settings. They apply to every
scenario; a scenario has only its own label, site and `start_time`.

| Case | `duration_days` | `step_minutes` | `horizon_mode` | `observer_height_m` | `visibility_margin_deg` |
| --- | ---: | ---: | --- | ---: | ---: |
| Geometric cases except rounded-score case | 1 | 360 | `geometric` | 2 | 0 |
| Rounded-score tie | 30 | 15 | `geometric` | 2 | 0 |
| Supported-terrain case | 1 | 60 | `terrain` | 2 | 0 |

Dates are scenario-specific. Do not replace different `start_time` values with a
common time. A result cross-check must use matching duration, step, horizon mode,
observer height and visibility margin. It must also use compatible
`model_version` and terrain dataset versions.

## Cross-check with an existing timeline fixture

The existing synthetic comparison fixture's `Synthetic A` scenario can be
compared with `contracts/examples/timeline-two-golden-windows.json` on the
fields represented in both fixtures:

- both use latitude `-89.44`, longitude normalized to `-137.9`, and the
  half-open period `2027-07-15T00:00:00Z` to `2027-07-16T00:00:00Z`;
- the comparison request uses one day, 360-minute steps, geometric mode,
  observer height 2 m and visibility margin 0°;
- the timeline result reports 360-minute resolution, geometric mode and the
  same 2 m observer height;
- both fixtures use `development-fixture-v1`, null terrain dataset IDs, and the
  same summary: 75% sunlit, 75% Earth-visible, 50% golden, 6 h longest window;
- the corresponding explicit score is `67.5`.

This is a deterministic fixture-to-fixture consistency check only. The timeline
result does not echo `visibility_margin_deg`, and there is no paired timeline
request fixture to prove that its source request used 0°. Both fixtures are
synthetic and do not establish a live comparison-to-timeline match. A live
acceptance run must retain the original requests and compare actual results
under identical settings and compatible model and dataset versions.

## Terrain provenance and completeness checks

Before a terrain comparison is considered valid, verify all of the following for
every requested scenario:

1. Terrain coverage reports `available: true` for the exact normalized
   coordinate, including enough valid surrounding data for the physical horizon
   calculation.
2. The calculation result carries the actual terrain dataset and processing
   version, coverage identity, and resolution. A display heightmap or scene mesh
   is not acceptable provenance for a physical horizon.
3. The comparison summary matches the corresponding terrain timeline under the
   same date, duration, step, horizon mode, observer height, visibility margin,
   model version and dataset version.
4. A geometric result has `terrain_dataset_id: null`; a terrain result never
   hides a geometric fallback.
5. If scenarios use different data/model versions, preserve and expose those
   differences. The current comparison result schema only has one top-level
   `meta.model_version` and one top-level `meta.terrain_dataset_id`; it cannot
   report per-scenario provenance. Multi-dataset or mixed-version terrain
   comparison acceptance is blocked until the contract is extended by agreement.

The [Stage 4 backend report](STAGE_4_BACKEND.md) records the registered source
as NASA/GSFC LOLA PGDA Product 90, dataset
`lola-product-90-09b7ca80f9e6a146`, 20 m/pixel, processing/model version
`lunar-south-polar-v1`, south polar stereographic metres, MOON_ME / JPL DE421,
and a 1,737,400 m reference sphere. Product 90 metadata covers 80°S–90°S and
includes the pole. The handoff records terrain readiness samples at the
Shackleton and Faustini reference points and a real terrain timeline at
Shackleton. This is prior Stage 4 evidence, not a Stage 5 comparison run. The
source metadata is summarized in [maps and terrain sources](../sources/maps-and-terrain.md).
The third candidate, Peak near Shackleton (PGDA Site07), has no agreed
coordinate in the application catalog; its terrain support cannot be accepted
by guessing a custom point. Product 78 local rasters remain excluded from
physical use because their vertical reference and full horizon coverage are not
verified.

## Acceptance execution notes

- Keep all controlled summaries separate from live Horizons results.
- Do not infer a visibility state from a site's name or latitude.
- Do not compare or rank a partial result as complete.
- Preserve the original request order for exact score and longest-window ties.
- UI acceptance must verify the returned rank and metrics, visible dates and
  modes, honest tie presentation, preserved request parameters when opening a
  scenario, correct selected-site marker/terrain, and communication direction
  from that exact selected point.
- The current repository has no comparison UI. UI acceptance is pending Sasha
  and Slavik's integration; the frontend must use backend scores and summaries,
  not recalculate them.
